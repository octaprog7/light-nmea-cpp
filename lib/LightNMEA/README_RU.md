# light-nmea-cpp

Сверхбыстрый парсер NMEA 0183 (GPS) для встраиваемых систем и Arduino.

> **Полная структура репозитория** (все файлы и их назначение): см. [корневой README](../../README.md#repository-structure). Сдесь описывается библиотека.

## Особенности

- **Header-only**: только заголовочные файлы
- **Без динамического выделения памяти в куче**: Не использует кучу (heap)
- **Целочисленная арифметика**: Не использует FPU
- **Высокая скорость**: 11 миллионов+ пакетов в секунду на x86 (R7 2700)
- **Малый размер**: ~1,3 КБ Flash-памяти, 52 байта RAM
- **Современный C++ (совместимость с C++17)**: таблицы поиска `constexpr`, подсказки ветвления `[[likely]]`, строгие перечисления (`enum class`)
- **Различные форматы вывода**: TXT, CSV, JSON, Compact
- **Преобразование единиц**: Скорость (км/ч, узлы, м/с), расстояние (м, футы, км)
- **Поддерживаемые сообщения/сентенции**: RMC, GGA, VTG, GLL

## Установка

### Arduino IDE

1. Скачайте ZIP-архив репозитория (Code -> Download ZIP) и распакуйте его
2. Скопируйте папку `lib/LightNMEA` в каталог `libraries` вашей Arduino IDE
   (например, `~/Arduino/libraries/LightNMEA`)
3. Перезапустите Arduino IDE: примеры появятся в меню
   Файл -> Примеры -> light-nmea-cpp

### PlatformIO

Добавьте в `platformio.ini`:

```ini
lib_deps = https://github.com/octaprog7/light-nmea-cpp.git
```

> Библиотека пока не опубликована в PlatformIO Registry, поэтому используется
> git-URL. После публикации можно будет использовать `octaprog7/light-nmea-cpp`.

Или соберите встроенные примеры прямо из репозитория
(у каждого примера свой `platformio.ini`):

```console
cd lib/LightNMEA/examples/BasicGPS
pio run -e pico          # или: esp32dev, bluepill
pio run -t upload -e pico
```

## Быстрый старт
```console
#include <lightnmea.h>

lightnmea::Parser parser;

void setup() {
  Serial.begin(115200);
  Serial1.begin(9600);  // GPS module
}

void loop() {
  while (Serial1.available()) {
    char c = Serial1.read();
    
    if (c == '\n') {
      if (parser.parse_line(buffer)) {
        const auto& data = parser.data();
        
        if (data.has_coordinates()) {
          Serial.print("Lat: ");
          Serial.println(data.latitude_deg(), 6);
          Serial.print("Lon: ");
          Serial.println(data.longitude_deg(), 6);
        }
      }
    }
  }
}
```

## Целочисленная модель данных

Все GNSS значения хранятся в виде **целых чисел с фиксированной точкой** (`int32_t`)
строго типизированных оберток, определенных в файле [`include/types.hpp`](include/types.hpp).
Сам парсер **не выполняет** никаких вычислений с типами `float` или `double`, поэтому он работает с максимальной
скоростью даже на микроконтроллерах без аппаратного FPU (AVR, Cortex-M0+/RP2040 и т. д.).
Преобразование в числа с плавающей запятой выполняется только по запросу с помощью вспомогательных функций, описанных ниже.

| Тип        | Масштаб       | Пример `raw`  | Физическое значение |
|------------|---------------|---------------|---------------------|
| `Latitude` | 1e-7 ° (×10⁷) | `481173000`   | 48.117300°          |
| `Longitude`| 1e-7 ° (×10⁷) | `115167000`   | 11.516700°          |
| `Speed`    | ×1000         | `22400`       | 22.400 узлов        |
| `Heading`  | 1e-2 ° (×100) | `8440`        | 84.40°              |

Допустимые диапазоны: `Latitude` -> [-90°·10⁷, +90°·10⁷], `Longitude` -> [-180°·10⁷, +180°·10⁷],
`Heading` -> [0, 36000) — конструктор выполняет автоматическую нормализацию.

Поля в `light_nmea::NMEAData`: `lat`, `lon`, `speed_kn_x1000`, `speed_kmh_x1000`,
`course_true`, `course_mag`.

### Как считать значения - рекомендуемый способ

Используйте встроенные вспомогательные функции:

```cpp
const auto& d = parser.data();
if (d.has_coordinates()) {
double lat = d.latitude_deg(); // double, градусы
double lon = d.longitude_deg();
}
float kn  = d.speed_knots(); // узлы (единица SOG в NMEA)
float kmh = d.speed_kmh(); // пересчитано из узлов
float ms  = d.speed_ms(); // пересчитано из узлов
float ctr = d.course_true_deg(); // истинный курс, градусы
float cmg = d.course_mag_deg(); // магнитный курс, градусы
```

### Прямой доступ и целочисленная арифметика: максимальная производительность для GNSS‑вычислений

Чтение поля `.raw` и преобразование с использованием целочисленной арифметики (без эмуляции FPU):

```cpp
int32_t kmh = light_nmea::knots_x1000_to_kmh_x1000(d.speed_kn_x1000.raw); // узлы × 1852 / 1000
int32_t mps = light_nmea::knots_x1000_to_ms_x1000(d.speed_kn_x1000.raw); // узлы × 463 / 900

light_nmea::Coordinate a(d.lat, d.lon), b(other.lat, other.lon);
int64_t d2 = a.distance_sq_to(b); // квадрат евклидова расстояния, без sqrt()
```

### Правила использования операторов (что допустимо для типов и почему)

Обертки предоставляют **только физически осмысленные операторы**; все они помечены как `constexpr noexcept`
и `inline` - неиспользуемые операторы не занимают места во Flash-памяти или ОЗУ:

- **`Latitude` / `Longitude`** - полный набор операторов сравнения + `is_valid()`. 
Отсутствуют `+` и `-`: сложение двух абсолютных координат - это логическая ошибка (смешение понятий). Для работы с дельтами или расстояниями
используйте «сырые» (`raw`) значения или метод `Coordinate::distance_sq_to()`.
- **`Speed`** - операции сравнения, `+`, `-`, `+=`, `-=`, унарный `-`, `is_stopped()`.
- **`Heading`** - `+`, `-`, `+=`, `-=` с автоматической нормализацией в диапазон [0, 36000); 
`==`, `!=`; `diff_to()` для вычисления кратчайшей знаковой угловой разности. 
Намеренно **отсутствуют** операторы `<`/`>`: для циклической величины понятие линейного порядка не имеет смысла
(например, 350° отстает от 10° всего на 20°, тогда как в «сыром» виде 35000 > 1000).
- **`Coordinate`** — `==`, `!=`, `is_valid()` (также отвергает начало координат `(0,0)`),
`distance_sq_to()`.

Основные рекомендации:

- Отдавайте предпочтение типизированным сравнениям (`a == b`) вместо сравнения «сырых» значений.
- Никогда не смешивайте единицы измерения: `Speed` использует единый масштаб (значение ×1000) для узлов, км/ч и м/с - сравнивайте или складывайте значения только **после** приведения к одной единице измерения, например, через `knots_x1000_to_kmh_x1000`.

## Информационная панель GNSS (TUI, Linux)

Интерактивная панель управления в терминале (компоновка из 4 окон: позиционирование / параметры GNSS /
динамика движения / статус подключения), считывающая данные через **последовательный порт** (USB-CDC /
USB-UART). Переписана с оригиналов на Python — `gnss_dashboard.py` и
`dash_utils.py` (см. версию проекта для MicroPython/Python):

```
SerialPort
-> SerialParser (буфер строк + detect_format())
-> CSV-поток с платы (12 полей) или «сырой» поток NMEA-0183 (light_nmea::Parser)
-> SYS_MSG: Системные сообщения микроконтроллера (имя модуля, программные сбросы, сторожевой таймер)
-> GNSS Dashboard (ncursesw)
```

Формат строки определяется автоматически (аналогично функции `detect_format()` в версии
на Python): панель распознает как подготовленный поток данных с платы (CSV, 12 полей,
разделенных запятыми), так и **«сырой» поток NMEA-0183** (сообщения вида `$XXYYY,...*HH`).

Как и в версии на Python, код разделен на две части: `examples/dash_utils.hpp`
(общие утилиты: GNSSData, LogWriter, AccuracyTracker, SerialParser) и
`examples/gnss_dashboard.cpp` (интерфейс на базе curses). Требуется `libncurses-dev` (ncursesw — входит в базовый состав Debian/Ubuntu):

```console
sudo apt install build-essential cmake libncurses-dev
cmake -S lib/LightNMEA -B lib/LightNMEA/out/build/release -DCMAKE_BUILD_TYPE=Release
cmake --build lib/LightNMEA/out/build/release --target gnss_dashboard -j
```

Или с помощью готового скрипта сборки (инкрементальная сборка, выбор режима
`Debug`/`Release`, флаг `--clean`):

```console
./lib/LightNMEA/examples/build_gnss_dashboard.sh
```

Запуск:

```console
./lib/LightNMEA/out/build/release/gnss_dashboard                      # авто: USB-CDC на 115200
./lib/LightNMEA/out/build/release/gnss_dashboard /dev/ttyACM0         # USB-CDC всегда работает на 115200
./lib/LightNMEA/out/build/release/gnss_dashboard /dev/ttyUSB0 9600    # USB-UART адаптер
```

Выход по клавишам `q`/`Q`/`ESC`; ошибки записываются в `mcu_debug.log`, лог данных —
в `gnss_log.csv`.

## Производительность

Пропускная способность нормирована относительно тактовой частоты процессора (МГц) — и, обратно, выражена как **количество тактов процессора на пакет**, —
что позволяет напрямую сравнивать платформы с разными частотами.

| Платформа | Пропускная способность | Нормированные показатели (пак./с·МГц / тактов/пак.) | Flash | RAM |
|----------|-----------|--------------------------------------|-------|-----|
| x86_64 (Ryzen 7 2700, 3,2–4,1 ГГц) | 7–14 млн пак./с [1] | ~2000–4400 пак./с·МГц (≈230–510 тактов/пак.) | — | — |
| Cortex-M0+ (RP2040, 133 МГц) | В 5–10 раз быстрее парсеров с плавающей запятой [2] | Измеряется на целевом устройстве [3] | ~1,3 КБ | 52 Б |

[1] Измерено с помощью [`bench_parser`](benchmarks/bench_parser.cpp) (GCC 14.2, `-O3 -march=native`,
смешанный поток RMC/GGA/VTG/GLL): в среднем 7,15 млн пакетов/с (8,2 млн пакетов/с при входном потоке
с 5% поврежденных пакетов) на машине, где находится репозиторий; 11–14 млн пакетов/с
на эталонном стенде (см. [корневой README](../../README.md#performance)).
Разброс ±20% обусловлен работой режима Turbo и нагрузкой.

[2] По сравнению с парсерами, использующими вычисления с плавающей запятой ([minmea](https://github.com/kosma/minmea),
[TinyGPS++](https://github.com/mikalhart/TinyGPSPlus)): у Cortex-M0+ нет модуля FPU, поэтому умножение
чисел типа `double` требует выполнения более 50 инструкций программной эмуляции FPU,
тогда как целочисленный конвейер выполняет ту же задачу за несколько операций ALU.

[3] Выполните измерения на своей плате, используя специальную прошивку для сравнительного
тестирования ([`benchmarks/firmware/`](benchmarks/firmware/)) — см. следующий раздел.

## Бенчмарк для микроконтроллеров (RP2040 / ESP32)

В репозитории есть ​​прошивка для PlatformIO, позволяющая сравнить **LightNMEA** с библиотеками
[minmea](https://github.com/kosma/minmea) и
[TinyGPSPlus](https://github.com/mikalhart/TinyGPSPlus) **на одной и той же плате**
([`benchmarks/firmware/`](benchmarks/firmware/),
исходный код: [`src/bench_compare_mcu.cpp`](benchmarks/firmware/src/bench_compare_mcu.cpp)).
Прошивка создает пакеты генератором из файла `nav_gen.hpp` (типов RMC/GGA/VTG/GLL) и выводит лучшие показатели производительности (по результатам N итераций) через последовательный порт (скорость 115200 бод) в единицах: пакет/с, нс/пакет, циклы/пакет и пакет/(с·МГц) (что позволяет напрямую сравнивать системы с разной тактовой частотой).

Требования: PlatformIO (версии 6.x). ```console
cd benchmarks
./build_bench_fw.sh pico            # сборка прошивки для RP2040 (доступны: esp32, all)
./build_bench_fw.sh pico upload     # прошивка платы
./build_bench_fw.sh esp32 monitor   # просмотр результатов (перезагрузите плату для повторного запуска)
```

Кол-во данных можно настроить с помощью флага сборки `BENCH_PACKET_COUNT` (по умолчанию 30 000),
а кол-во проходов - с помощью `BENCH_PASSES` (по умолчанию 3; учитывается лучший результат):

```console
BENCH_PACKET_COUNT=100000 ./build_bench_fw.sh pico
```

> **Примечание о размере прошивки.** Само приложение для тестирования занимает ~9 КБ, 
> однако ядро ​​Arduino для ESP32 (ESP-IDF HAL + newlib stdio) добавляет
> фиксированные ~280 КБ независимо от кода приложения: это около **22% от
> раздела приложений объемом 1,31 МБ** по сравнению с ~3,7% (78 КБ) при использовании Pico SDK.
> Это накладные расходы платформы, а не код парсера - сама библиотека LightNMEA занимает
> ~1,3 КБ во флеш-памяти и 52 байта в ОЗУ. Не сравнивайте напрямую абсолютные показатели
> двух плат; используйте нормализованные метрики (циклов/пакет, пакет/с·МГц),
> которые выводит бенчмарк.
